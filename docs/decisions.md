# Decisions

## DECIDED

- Master is the current Work proxy.
- Temporal snapshots are mandatory.
- Evaluation is out-of-time.
- Historical baselines come before ML.
- Time Machine uses historical out-of-time predictions.
- master_id is a unique key in masters_df (verified, 0 duplicates across 2,589,349 rows).
- status is dropped from releases_df (100% null, not present as an XML attribute in this dump, verified against raw XML).
- year == 0 in masters_df is treated as missing and converted to NaN, not as a real date (6.7% of rows). The decision was logged back when it was made but the notebook cell that applies it to masters_df was never written (the equivalent fix for standalone_candidates was written and ran fine), so 100,877 zero-year master rows leaked into works_df uncleaned, inflating reissue-candidate year gaps into the hundreds or thousands of years. Added the missing masters_df["year"] fix in the notebook and re-ran sections 7 to 9 on 2026-10-06.
- work_id = master_id when master_id != 0, otherwise a synthetic id is required (41.6% of releases_df have master_id == 0).
- Masters with artist_names in {"Various", "Unknown Artist", "No Artist"} are excluded from the Works dataset (174,000 masters, 6.7%, verified via value_counts).
- Masters tagged Non-Music are excluded from the Works dataset (38,685 masters, not music even when released by a real artist).
- Masters tagged Children's are excluded from the Works dataset (22,390 masters, not relevant to musical style prediction).
- master_id 376240 ("Dummy1") is a placeholder/test record (empty artist_ids, no genres, no styles, year 0) and is dropped.
- Masters marked data_quality == "Entirely Incorrect" are dropped (139 masters, flagged unreliable by Discogs' own community).
- Masters marked data_quality == "Needs Vote" are kept (2,155 masters, unconfirmed but not known to be wrong).
- Masters flagged is_compilation or is_unofficial (via a representative release's format_descriptions) are excluded from the Works dataset (165,172 compilations, 32,158 unofficial, 8,421 overlap).
- release_year > 2026 (snapshot date) is treated as missing inside _add_release_year itself, not just in standalone_candidates. Gap found: of 38,670 master years recovered by recover_missing_master_years, 0 were > 2026, no rows were actually affected, but the exclusion only lived in the standalone_candidates cell, so a future-dated release could in principle have been picked up as a recovered master year. Fixed in src/works.py so every caller shares the rule. Re-ran notebook 01 end to end on 2026-10-08, every checkpoint parquet is byte-identical (md5) to the pre-fix run, confirming no shift; notebook 02 was not re-run since nothing changed upstream of it.
- Standalone releases (master_id == 0) belonging to artists with 3+ standalone releases become synthetic Works (recovers 388,610 artists otherwise lost entirely under Masters-only).
- The same exclusion rules applied to masters_df (non-artist placeholders, out-of-scope genres, Entirely Incorrect data_quality, compilation, unofficial) are applied to these standalone releases: 899,514 + 685,589 + 826 + 401,541 + 182,761 excluded (with overlaps), 4,218,546 remain.
- year == 0 and year > 2026 in standalone_candidates are treated as missing, same rule as masters_df (115 zero-year rows, 1 future-dated release).
- works_df combines masters_df (2,015,417 rows, work_source="master") and standalone_candidates (4,218,546 rows, work_source="synthetic") into one unified Works table, 6,233,963 rows total, work_id verified unique.
- Exact duplicates in works_df (same artist_id, normalized title, year) are removed, keeping one per group: master preferred over synthetic, then smallest work_id. 119,492 rows removed (107,537 groups), works_df now 6,114,471 rows.
- Re-ran the above after the year==0 fix: exact-duplicate removal now resolves to a slightly different split (counts shift because some former year==0/year==NaN mismatches no longer collide or separate the same way), works_df before reissue handling stands at 6,114,471 rows, unchanged in final size.
- Re-ran the above again after adding the Master missing-year recovery step (recover_missing_master_years in src/works.py, called right after works_df is first built, before any dedup or title filter runs, see the recovery entry below): exact-duplicate removal now resolves to 119,043 rows removed (107,208 groups, was 119,492/107,537), works_df before reissue handling now 6,114,920 rows (was 6,114,471), for the same reason as the year==0 re-run above, a Master's year changing from missing to a real recovered value changes which rows collide on the dedup_key. Every downstream filter count through the rest of the pipeline shifts by a similarly small amount for the same reason; the new final checkpoint figure is logged separately below.
- Works tagged reissue/repress/remaster (via format_descriptions) that share artist_id + normalized title with an earlier-year work by the same artist are removed, keeping the earliest work in each group (the earliest row can never match its own condition, so it survives automatically, no separate keep-rule needed). Verified sane after the year==0 fix: year gap median 12, max 89 (Robert Johnson, 1930s recordings reissued in 2026); only 20/4758 candidates (0.42%) have a generic title ("Untitled", "Live", "Demo"), accepted as noise. 4,758 rows removed, works_df now 6,109,713 rows.
- Live recordings are excluded from the Works dataset entirely (same reasoning as compilations/unofficial: a performance of existing material, not a new stylistic work). No reliable Discogs tag exists for this (format_descriptions and style both checked, neither carries a "Live" value), so detection is title-only (regex \blive\b, case-insensitive). Checked the word following "live" in matching titles: dominated by "at"/"in"/"from"/end-of-title/parenthetical patterns consistent with real live albums, accepted residual noise in both directions (idiom false positives like "Live To Tell", untitled-as-live false negatives). 92,531 rows removed, works_df now 6,017,182 rows.
- "Greatest Hits" works that slipped through the earlier is_compilation exclusion (Discogs did not tag them Compilation in format_descriptions) are removed by title match ("greatest hits", case-insensitive). Small population (1,622 rows, 0.027%), same reasoning as the Live exclusion: a compilation of previously released material, not new creative work. works_df now 6,015,560 rows.
- Other clear compilation-type titles that also slipped through is_compilation ("best of", "anthology", "box set", "discography", "b-sides"/"bsides", "rarities") are removed the same way. Sample of 20 confirmed overwhelmingly real compilations, one accepted edge case ("Best Of Me", could be an original song title, same order of noise as Live/reissue). 6,622 rows removed, works_df now 6,008,938 rows.
- "Remixes"-titled works (regex remixes|remix album) are removed: a package of mostly third-party remixes of an already-existing track, credited back to the original artist, same reasoning as reissue (repackaging, not a new creative step). Sample of 20 was uniformly clean, no ambiguous originals. 24,917 rows removed, works_df now 5,984,021 rows.
- "Tribute"-titled works (regex \btribute\b) are removed: overwhelmingly "Tribute To [other artist]", covering/performing someone else's material as homage, not the credited artist's own new work. A handful of standalone matches ("Tribute", "My Tribute") don't name a target and could be original compositions, accepted as the same order of noise as other patterns. 5,394 rows removed, works_df now 5,978,627 rows.
- "acoustic" alone (3,824 matches) was too ambiguous to exclude (counterexample: "Acoustic Soul" by Fink is a genuine original studio album, not a redo), moved to CUT. Narrowed to the parenthetical "(Acoustic)" suffix pattern instead (1,060 matches): sample of 20 confirmed uniformly "Song Name (Acoustic)", a redo of an existing song, same reasoning as Live. 1,060 rows removed, works_df now 5,977,567 rows.
- "(Instrumental)" parenthetical suffix (757 matches, went straight to the narrow pattern given the acoustic precedent, broad "instrumental" never tested): a vocal-less version of an existing song. Sample of 20 confirmed the pattern. 757 rows removed, works_df now 5,976,810 rows.
- "unplugged" (983 matches) are removed: overwhelmingly MTV-Unplugged-style live acoustic performances of already-existing songs, same reasoning as Live. Sample of 20 was uniformly clean. 983 rows removed, works_df now 5,975,827 rows.
- "radio edit"/"radio version"/"bbc session" (1,735 matches combined) are removed: a shortened derivative edit of an existing track, or a BBC-style radio session re-performing existing material, same reasoning as reissue/Unplugged. "session" alone was checked and discarded (too generic, mostly original recording-session albums like "Tutorial Sessions"). 1,735 rows removed, works_df now 5,974,092 rows.
- Placeholder-artist leak fixed: the original Various/Unknown Artist/No Artist exclusion was case-sensitive exact match, so "various"/"VARIOUS" and similar case variants slipped through (1,422 rows, found while reviewing Greatest Hits titles). Removed by a case-insensitive pattern covering Various/Various Artists/Unknown/Unknown Artist/No Artist/N A/VA. works_df now 5,972,670 rows.
- Fixed the root cause of the placeholder-artist leak at the source (2026-10-06): the masters_df and standalone_candidates exclusion cells now compare artist_names_str.str.lower() against a lowercased NON_ARTIST_PLACEHOLDERS set, instead of an exact case-sensitive match. Re-ran the full notebook from that point on; downstream counts shifted slightly (see updated numbers above). A final placeholder-leak QA check at the end of works_df cleaning still finds 1,422 remaining, other variants (bare "Unknown", "N/A", "VA") the original exclusion set didn't cover, removed there, 0 remaining after.
- Similarity-only fuzzy-dedup (rapidfuzz token_sort_ratio, bands 85-90/90-95/95-99), with no guard against numbered-series titles, was rejected as a filter on top of the existing exact-match title_normalized dedup: checked at full scale across all 699,079 multi-work artists / 5,774,455 works in works_df (window-10 alphabetical blocking per artist, no cap or skip), numbered/episodic series entries (radio show episodes, Vol./Partie/roman-numeral sequences) dominate every band as false positives, with a handful of plausible true duplicates (typos, accent variants) scattered across bands and no clean score separation from the noise. Superseded by the guarded version below, which fixes this false-positive pattern and is the one actually applied to works_df.
- Fuzzy-dedup implemented in src/works.py (remove_fuzzy_duplicate_titles): within each artist_id, using window-10 alphabetical blocking, pairs scoring >=90 on rapidfuzz token_sort_ratio are collapsed unless a number/roman-numeral guard applies. The guard strips embedded digit runs from every token (so "mix4" vs "mix7", "S01E03" vs "S01E05" are also caught, not just space-separated numbers like "Vol. 2" vs "Vol. 3") and skips the pair if titles are only different by that numeric content. Threshold chosen because a stricter 95+ cutoff would have missed known true duplicates in Bing Crosby's catalog (scores 89.5 and 91.4). Tie-break on a collapsed pair keeps the earlier year (missing year treated as latest), ties broken by smaller work_id. Verified at full scale against works_checkpoint.parquet (6,114,471 rows): removed 21,846 rows (0.36%), works_df now 6,092,625 rows. That check ran the filter in isolation against the stale pre-title-filters checkpoint (6,114,471 rows), not at its actual position at the end of the integrated pipeline. Re-ran the full notebook top to bottom from a fresh kernel on 2026-10-07 (see the checkpoint-overwrite fix below), confirming the filter's real position after all title filters (pre-fuzzy-dedup works_df at 5,972,670 rows, matching the figure logged above): removed 20,854 rows, works_df now 5,951,816 rows. This is the correct, current figure; the 21,846/6,092,625 numbers above are superseded. Two accepted known limitations: (1) "Vol."/"Volume" abbreviation mismatches aren't caught by the guard, so a small number of genuine volume-series pairs may still collide (full-dataset band sampling showed minimal residual noise after the guard, so this looks rare); (2) shared-template titles with a non-numeric varying word (e.g. a medley "X / Y" title where Y differs, such as "White Christmas / The First Nowell" vs "...The First Snowfall") can produce false positives, spot-checked at 1 of 11 in the Bing Crosby test. Applied at the end of the cleaning pipeline in notebooks/01_cleaning_eda.ipynb, right before the final checkpoint save.

Checked at full scale (not sample) against works_checkpoint_fuzzy_dedup.parquet: 951 of those groups (1,918 rows) share an exact (label name, catalog number) pair between two or more entries, where the shared catalog number is real, not a blank/placeholder value ("none", "", "n/a" are never accepted as evidence; EMPTY_CATALOG_NUMBERS in src/works.py). A further 2,943 groups share only a blank/placeholder catno and are deliberately excluded, since two unrelated self-releases can easily both be uncatalogued. A 30-row sample of the 951 real-match groups was uniformly clean (same recording re-released under a different year/format, just never tagged by Discogs). Collapsed with the same tie-break as the fuzzy-dedup filter: earliest year survives (missing year sorts last), ties broken by smaller work_id; matches spanning 3+ entries in one group are resolved as connected components, not just pairwise, so a transitive chain collapses to one survivor. Verified at full scale against works_checkpoint_fuzzy_dedup.parquet (5,951,816 rows): removed 967 rows (951 groups, 1,918 rows involved minus 951 survivors), works_df now 5,950,849 rows. - Mass-upload artist exclusion implemented in src/works.py (remove_mass_upload_artists), resolving the PENDING question about "Nosferatu 1922" (artist_id 6391827): rule is general, not hardcoded to that artist_id, checked across every artist_id in works_df (not just the top few hundred by volume). Without the 50-work floor, the same three-signal rule matches 165 artists / 2,301 rows, but 164 of those have only 2-18 works, too few for the synthetic-share and 2-year-window signals to mean anything (both are almost automatically satisfied by a tiny, recently-entered catalog); the floor was added specifically to exclude that noise. - Master missing-year recovery implemented (recover_missing_master_years in src/works.py, 2026-10-08): a read-only check first found that of the 98,728 master-side works missing a year in the then-final works_checkpoint.parquet (5,948,995 rows), 37,473 (37.9%) had at least one Release with a parseable, non-zero released year, overwhelmingly with 2-5 candidate Releases (32,344), not a handful of oddly-linked masters (29 at most in the sampled set). This is real data already present in releases.parquet, not an inference or a fabrication, so the recovery is applied unconditionally: for each Master still missing a year, the earliest valid year among its own Releases (same _add_release_year parsing already used elsewhere) is taken as the recovered year. Inserted right after works_df is first built, before any dedup or title filter, since the exact/fuzzy/catalog-number dedup survivor tie-break all use year. Re-ran the full pipeline top to bottom from a fresh kernel (2026-10-08): at the point of recovery, 101,543 master works are missing a year, 38,670 (38.1%) are recovered. The final works_checkpoint.parquet now has 5,949,217 rows (was 5,948,995, superseded), with 61,388 of 1,951,057 master-side works still missing a year (3.15%, was 5.1%) and overall missing-year share down to 8.58% (510,364 of 5,949,217 rows, was 9.19%).
- Genre disparity in the recovery above is non-uniform and NOT resolved by it: a read-only per-genre breakdown found recovery rate correlates strongly negatively with each genre's original missing-year rate (Spearman r=-0.809, p=0.0026, n=11 genres), meaning genres that already had the easiest time (Rock 53.8% recovery, Electronic 47.9%, Blues 50.1%) recover at roughly 50%, while the hardest-hit genres (Latin 32.8%, Folk/World/&Country 30.2%, Reggae 38.9%) recover at the lowest rates. Every genre's absolute missing-year count only improves (Folk/World/&Country gets the single largest absolute recovery, 10,631 rows), but the relative disparity between genres does not close, if anything it widens slightly (missing-year spread went from ~17x to ~18x between the worst genres and Electronic, see the DECIDED entry below). Accepted as an unresolved limitation of this recovery, not presented as having fixed the genre equity gap.

- Missing-year artist dropout: do not drop artists/works with missing year. Rationale (2026-10-08): dropping the 173,938 artists (16.8% of 1,034,756) who have missing year would remove 1,995,677 works (33.6% of the 5,949,217 total), with a material genre/style skew in the dropped population (affected artists over-indexed in high-missing-rate genres: Latin 25.7%→36.6%, Folk/World/&Country 21.5%→37.2%, Reggae 23.0%→31.1%, Punk 2.6%→18.8%, Folk style 11.7%→29.5%; under-indexed in low-missing-rate genres: Electronic 1.5%→11.3%, Tech House 0.4%→4.8%; range of differences +5% to +17.8pp). Not a neutral trim of noise, but a selective removal of entire categories. Approach: keep missing-year works; add an explicit year_missing boolean feature; use a model family that splits on missingness natively (LightGBM/HistGradientBoostingClassifier), not sklearn's default RandomForest. Supporting numbers: 173,938/1,034,756 artists affected; of those, 39,706 fully missing (all works undated), 134,232 partially missing (mixed); 510,364 of their 1,995,677 works missing year (25.6%); genre/style distribution skew documented in the pasted analysis from notebooks/02_eda_visualization.ipynb re-run 2026-10-08 (before finalizing train/test split, revisit this decision if model performance on missing-year works drifts significantly at modeling stage).
- WHEN target is measured at year level, snapshots stay one per dated work (2026-10-10, src/snapshots.py): next_1y/next_2y use the gap to the artist's next year with activity after the snapshot's own year (always >= 1), not the next individual Work. Reason: 63% of dates are year-only, and with the next-Work definition 48.2% of snapshots (56.2% with 3+ prior works) had the next Work in the same year (gap 0), forcing next_1y/next_2y positive (76.2%/85.9% base rates). Collapsing to one snapshot per artist-year was tried first and replaced to keep the per-work unit. Re-validated on the full checkpoint (5,438,765 snapshots, 510,357 undated and 95 no-artist works dropped): next_1y 51.8%, next_2y 64.1% (62.4%/74.0% with 3+ prior works), 66.1% of next active years fall exactly 1 year later, and an independent recompute of both targets matches exactly. Added works_this_year (whole-year count, so it includes later same-year works), work_source/genres/year_missing pass-through, a deterministic within-year order (see the so-far entry), and 2025 as the last complete year for censoring (the 2026-09-01 dump makes 2026 partial). Known effect: next_1y rises with works_this_year (29.3% for 1 work, 86.3% for 5+), so productivity is a strong WHEN signal.
- new_style comparison fixed in src/snapshots.py (2026-10-10): the next Work is now compared against every Work up to and including the snapshot's Work, matching src/eda.py and the docstring. The earlier code left the snapshot's own Work out of the seen set, so a style repeated from the immediately preceding Work was wrongly flagged new (37.3% overall and 21.5% with 3+ prior works, now 26.7% and 18.8%, against 23.5%/18.1% in the EDA base rate).
- Work-type feature added at snapshot level (src/snapshots.py, classify_work_type): album-like = Album/LP/EP/Mini-Album, single-like = Single/Maxi-Single, other = everything else. Over all 5,949,217 Works: 43.5% album, 21.3% single, 35.2% other. "Other" is mostly untagged physical or digital formats (MP3 24%, 7" 23%, 45 RPM 22%, 12" 16% of the other bucket) plus 185,784 Works with no format description at all, so single-like is a lower bound. Snapshot features: is_album_like, is_single_like, albums_so_far_this_year, singles_so_far_this_year (model-safe) and the whole-year albums_this_year, singles_this_year (descriptive only, see the next entry).
- Within-year productivity features split into model-safe and descriptive-only (2026-10-10, src/snapshots.py): works_so_far_this_year (works up to and including this one in the artist/year/work_id sort order), albums_so_far_this_year and singles_so_far_this_year are the modeling-facing features. works_this_year, albums_this_year and singles_this_year count the whole year, so they include same-year works that come after the snapshot's work and leak future information within the year; they stay in the output for EDA only and are marked in the docstring as not safe as model inputs. Re-check on the full checkpoint (5,438,765 snapshots), next_1y by works count: 1 work 38.7% (so far) vs 29.3% (whole year), 2 works 61.2% vs 52.3%, 3-4 74.3% vs 67.0%, 5-10 87.2% vs 83.6%, 11+ 92.4% vs 92.2%; Spearman with next_1y 0.351 (so far) vs 0.445 (whole year). On first-of-year rows only (all have works_so_far = 1, so the feature carries no information there), the whole-year count alone still separates next_1y from 29.3% to 92.0%, which is the leaked part: about a fifth of the correlation (0.445 to 0.351) disappears, and the rest of the signal (38.7% to 92.4% across the buckets) is genuine within-year productivity known at the snapshot. Caveat: the within-year order is not real chronology (the data only knows the year), so the so-far features are a proxy, and the strictly leak-free cutoff is the year. The first version ordered same-year works by work_id, which put every master before every synthetic work (synthetic ids carry the 10_000_000_000 offset); replaced the same day by a seeded pseudo-random order (hash of work_id plus WITHIN_YEAR_ORDER_SEED = 1, reproducible and independent of input row order). Re-check: Spearman of works_so_far_this_year with next_1y unchanged at 0.351 and the bucket rates unchanged to 3 decimals (38.7%, 61.2%, 74.3%, 87.2%, 92.4%), so the remaining signal is genuine productivity, not a source artifact; in the 358,052 artist-years that mix masters and synthetic works, the first slot is now synthetic 52.5% of the time (54.3% of those works are synthetic), was 0% by construction. The same order drives history_count, years_since_last and the next-work comparison in new_style.

## Hypothesis Testing

**Hypothesis 1**: Does an artist's new-style introduction rate change with how many prior works they have? H0: new_style and prior_work_bucket are independent. H1: they are dependent. Caveat: transitions from the same artist are not fully independent, so the p-value is overstated; the rate gap is the stronger evidence.

**Method**: Chi-square test of independence, computed on 3,254,604 eligible transitions (min_previous_works=3). Transitions bucketed by prior-work count into five groups: 3-5 prior works, 6-10, 11-20, 21-50, 51+.

**Results** (notebooks/02_eda_visualization.ipynb cell hypothesis testing, executed 2026-10-08):
- 3-5 prior works: 927,574 transitions, 26.88% introduce new style
- 6-10 prior works: 729,148 transitions, 20.64% introduce new style
- 11-20 prior works: 632,029 transitions, 15.72% introduce new style
- 21-50 prior works: 576,937 transitions, 11.18% introduce new style
- 51+ prior works: 388,916 transitions, 6.20% introduce new style

**Chi-square test**: chi-square = 109,737.05, p-value < 0.000001, degrees of freedom = 4. **Result: REJECT null hypothesis** (p < 0.05).

**Interpretation**: The new-style introduction rate varies significantly by prior-work bucket, with a strong monotonic decline as artists accumulate more prior works. This is not noise; artist history length is a real signal that predicts stylistic consistency. The effect is large: a 4x difference between the lowest (6.20%) and highest (26.88%) buckets.
